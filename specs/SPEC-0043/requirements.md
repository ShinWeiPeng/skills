## User Stories
各專案可在確認 SPEC 前看見 OS 與執行環境的具體規劃及選擇理由。

## Requirements
| ID | Requirement |
|---|---|
| REQ-001 | OS 規劃依專案需求決定：已確認 OS 則沿用；未定案才比較裸機、RTOS 或一般 OS，提出理由供使用者確認。多 OS 支援另依明確需求提出，不作全域預設。 |
| REQ-002 | OS 規劃九項逐項判定適用性：執行環境、執行單元、模組對應、排程與時序、同步與通訊、資源配置、生命週期、OS 相依邊界、驗證方式。適用項交代具體方法與理由，不適用項說明原因；時序分析與量測深度依專案風險及既有規範決定，不降低已有強制要求。未知資訊保持待確認／待驗證，不得當作不適用或虛構數據。 |

| REQ-011 | OS 能力與使用條件採方案 B：列出實際需要的 OS 能力、允許的呼叫環境及等待限制；固定條件於設計／建置核對，部署或執行期才可確定的必要條件於初始化或使用前確認。未滿足時拒絕受影響操作並依異常契約報告，不將其他能力或環境視為等價；替代方法須事先確認並符合相同必要語意與安全要求。具體門檻由專案提供，範例不得成為全域預設。 |
| REQ-012 | 執行單元配置採方案 C：預設按資料處理階段拆分，以有界通道連接；依工作負載與分析可提出合併，需呈現理由及選擇。交代排程、交接、緩衝與生命週期成本，仍須符合 OS 能力、容量與時序，硬／軟即時工作保留既有候選分析義務。不將處理階段與邏輯模組混同。 |
| REQ-013 | Task 間通訊必須使用目標 OS 支援的通訊工具，涵蓋資料、事件與訊息，可依契約選擇 mailbox、queue、event 或適當 OS 機制；不得以未宣告的共享全域／直接跨 Task 修改對方私有狀態代替交接。每通道工具、容量、呼叫環境及資料所有權須明確。功能模組透過公開通道／port 契約使用，OS API／handle 等實作依既有 adapter 邊界治理；工具不能代替有效期間、滿載及交付語意的設計。 |
| REQ-014 | 每個 Task 間通道明定交付契約：資料／命令／事件紀錄／狀態通知的用途、OS 工具、有限容量、排序及接收對象、逐筆保留或依已確認用途合併、滿載／等待／逾時／停止處置、傳值或傳引用及持有／釋放責任，並區別送入工具、接收及處理完成。只通知不等於逐筆交付；允許合併時仍保留必要進度或狀態。既定異常通知覆寫及持續故障狀態規則沿用。 |
| REQ-015 | 同步與等待：私有可變狀態由擁有者修改，其他 Task 經 OS 通道提出請求；共享資料明定存取權限、同步及回收條件，通道交接不代替區塊保護。使用鎖須說明保護對象、持鎖範圍、OS 支援能力及等待限制；多鎖／通道等待須有可檢查的避免互等策略，時序分析涵蓋優先權反轉。失敗／取消／逾時依契約釋放本操作持有的鎖與資源，保留仍被使用資料；ISR／受限路徑只使用符合環境與阻塞限制的方法，取得失敗依通道及異常契約處置。不強制所有共享資料使用 mutex。 |
| REQ-016 | OS 資源須記錄容量／數量、擁有者、配置時機、預算依據及回收條件，包含實際使用的 Task stack、queue／mailbox、同步物件、timer、handle、共享資料及在途引用上限；整體核對同時運作情境與 OS 開銷，不重複計算共享區塊。設計列預算及估算，未知標待確認，實作後取得必要量測與餘裕依據。建立失敗／耗盡不得當作成功，依已確認容量與異常契約拒絕、背壓、丟棄或停止；不得無界擴容或暗改配置策略。取消及重啟须驗證回收，不得反覆累積。具體數值由專案決定，不作全域門檻。 |
| REQ-017 | 排程與時序：依工作負載區分硬即時、軟即時與一般工作，Task 明定觸發、頻率／突發限制、優先權、執行與等待預算及必要核心配置。端到端期限／新鮮度／吞吐納入排隊、聚合、鎖阻塞、交接、中斷及 OS 開銷，不以平均耗時或 CPU 利用率單獨證明期限。即時工作沿用既有候選比較与符合排程器的分析，設計採有依據的保守預算，實作取得必要界限與證據；硬期限未滿足不能合格，軟期限容忍有明確量化契約。驗證正常、尖峰及相關慢消費者情境，不以未支援或錯誤排程模型宣稱通過。所有數值由專案需求與平台能力決定。 |
| REQ-018 | Task 與 OS 資源生命週期須明定協調擁有者、狀態及初始化／就緒／啟動／停止／取消／重啟順序；建立 Task 不等於服務就緒，啟動前確認必要通道與接收者就緒。部分建立失敗安全收尾本次持有資源並依契約報告。停止先關閉新工作准入，依通道用途在期限內排空或取消，透過 OS 工具協調結束與回覆；逾時須明示未完成，不得釋放仍被使用資料或銷毀仍被執行活動使用的 OS 物件。重啟前確認舊活動已隔離或結束，處理舊訊息與引用，防止被當成新請求；失敗及重複重啟不得無界重試或累積資源。具體狀態與確認機制由專案選定，沿用既有 Stop、異常與模組狀態規則。 |
| REQ-019 | OS 專業檢查採設計、實作、驗收分工：設計核對九項適用性、Task／模組／通道對應、OS 能力與呼叫環境、同步及容量／時序／生命週期契約，保留必要可行性分析；實作核對程式與確認設計、OS API／adapter 邊界、建置及適用的滿載、逾時、建立失敗、取消與重啟測試；驗收依風險與既有規範取得適用目標環境的 stack、排隊／等待、排程／期限及停止／重啟證據，主機模擬不得替代必需目標證據。每項檢查引用規則 ID、設計 ID／版本及 AC，分別標記工具判定、人工審查及執行期證據；缺失只阻擋相依工作，整體驗收未滿足不得宣稱完成。通用機制由 SPEC-0044 定義，本 SPEC 維護 OS 檢查內容與映射。 |
| REQ-020 | OS 設計欄位依來源分工：architecture/designs/platform/ 維護 OS／版本、CPU／核心、實際可用 RAM、OS 能力與呼叫限制、排程器能力及依據等平台事實；architecture/designs/execution/ 維護對應部署組態的執行設計並引用平台版本。執行設計包含執行單元／模組對應、排程／時序、通道、同步、資源、生命週期及驗證引用七組欄位，具體欄位依 DISC-021 採用內容。模組介面及資料流依 ID／版本引用其設計文件，各數值有單位與估算／量測依據，未知與不適用分開且有說明；每項資料只由所屬文件維護。通用 ID／版本／格式機制由 SPEC-0044 定義。 |
| REQ-021 | OS 程式規則採七組 ID：OS-CAP-001、OS-EXEC-001、OS-CHAN-001、OS-SYNC-001、OS-RES-001、OS-TIME-001、OS-LIFE-001，強度均為 MUST，依 DISC-022 所列條件適用。正式完整條文保留 REQ-011 至 REQ-018 全部已採用要求；OS 隔離沿用 MOD-DEP-005、MOD-DEP-006、TYPE-002。純規則僅含規則 ID、強度、適用條件、程式要求；Task 候選拆分／合併、文件欄位及檢查步驟歸各自流程。不適用有理由，未知不能當不適用，不增設全域數值門檻，其他既有規則仍適用。 |
