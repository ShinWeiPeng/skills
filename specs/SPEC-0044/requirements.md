## User Stories
各設計各自維護，SPEC 可讀且可追溯確認版本，不因格式準備阻礙正常討論或已授權工作。

## Requirements
| ID | Requirement |
|---|---|
| REQ-003 | SPEC 採分檔及引用方式組織，每種不同設計在各自文件維護；主檔提供入口與關聯，避免所有設計集中於單一 SPEC。具體目錄、文件生命週期、版本綁定及確認／授權邊界待討論。 |
| REQ-004 | 採專案共用設計文件：每個模組、資料流及 OS／執行環境設計有一份目前版本，各 SPEC 引用相關文件及確認版本；候選修訂與歷史版本須有明確狀態，不能使新草案改動舊確認內容。具體版本保存與授權前草案機制待確認。 |
| REQ-005 | 受影響設計採候選版本管理：每份 SPEC 只為需修改的設計保存候選，引用原設計 ID 及基準版本；未受影響設計直接引用。確認與執行授權後，核對正式基準未改變才更新共用設計；基準不同先處理差異，不直接覆寫。舊 SPEC 可追溯固定舊版，新 SPEC 引用已確認新版；每個版本只有一個維護位置，歷史版本不可修改。 |
| REQ-006 | 採 Markdown 設計文件為資料來源：各設計檔以固定欄位、表格或結構化區塊提供可讀且可解析內容，由工具產生整合 manifest 與相關圖表；同一設計資料只在來源文件維護，不再手動同步修改 manifest。需一併調整格式、解析器、產生器、檢查器及既有來源遷移。 |
| REQ-007 | 採用目錄分工：specs/SPEC-####-名稱.md 為精簡入口；specs/SPEC-####/ 保存 requirements.md、acceptance.md、discussion.md、references.yaml 及 candidates/。architecture/designs/ 依 platform、execution、modules、flows 分存目前 Markdown 設計，architecture/history/ 保存不可修改的確認版本，architecture/manifest.yaml 與 generated/ 為生成產物。references.yaml 僅保存設計 ID、版本及內容雜湊，不重複設計內容；候選僅含受影響設計。 |
| REQ-008 | 分檔後以整份變更一次確認與授權：先呈現 SPEC 摘要、變更清單及需求／驗收／設計文件連結，確認綁定當次文件集合及相关設計依賴的固定版本。「開始執行」對應同一集合，執行前重新核對；無關模組不需重新確認。需求、介面、設計方法或驗收條件實質改變才重新確認及授權；單純追加討論紀錄或由相同來源確定性重新產生相同內容，不重新要求授權。 |
| REQ-009 | 討論階段可由治理工具保存本次 SPEC 主檔、需求、驗收計畫、討論紀錄、引用清單及候選設計，並在受限暫存／證據區產生草案檢查輸入與實際紀錄。正式設計、正式 manifest、程式與測試實作仍須確認及本次執行授權；Git 提交、安裝及發布依各自授權。草案 PASS 僅代表實際完成的設計檢查，不得把未實作／未量測結果視為已驗證。 |
| REQ-010 | 分階段檢查：設計階段檢查欄位、引用、所有權、容量／時序預算、具體方法及驗收計畫，必要可行性分析依既有規範，不要求尚未實作的結果；實作階段核對程式與設計、建置及適用測試；驗收階段核對各 AC 及必要量測／實機證據。缺資料僅阻擋相依決策；同範圍錯誤沿用授權修正重測，需求或設計契約改變須重新討論確認及授權；缺驗收證據不得宣告完成，已授權的證據收集可繼續。 |
| REQ-011 | 設計欄位格式採方案 B：固定標題與 Markdown 表格承載一般／扁平欄位，巢狀或條件式資料使用文件內由格式規範指定的 YAML 區塊。平台、執行、模組及資料流各由領域格式定義欄位及承載位置，同一欄位不得在表格與區塊兩處手填或任意混用；文字說明不代替必要欄位。文件識別與格式版本固定，工具只讀取已定義格式；缺欄位、重複 ID、錯誤型別／單位及版本引用須定位到文件與欄位，不自行猜讀。Markdown 仍為設計來源，manifest 及圖表為生成產物。 |
| REQ-012 | 多檔更新先在候選／暫存區完成整套來源、欄位、引用版本及生成產物檢查；取得本次正式更新授權後，套用前核對基準，差異保留處理，不覆寫其他修改。全套驗證成功才標記生效；失敗／中斷保存候選、進度、原因與恢復資料，上一套完整確認版本可追溯。部分寫入標記未完成，正式讀取僅接受可驗證的完整版本；不得以混合新舊內容繼續相依程式修改。恢復核對原基準／本次已写入內容，保留後來修改，安全重試或恢復；不得以 Git 提交或強制回退代替此機制。具體方法與失敗／中斷／版本競爭驗收列於實作方案，不假設多檔檔案系統寫入天然同時完成。 |
| REQ-013 | 更新／生成／檢查失敗時，Codex 須承擔解決責任：持續查明原因，執行已授權且不改契約的必要修復，驗證修復成功，再恢復並完成原本工作；不得以保存進度、標記失敗、改做不相依工作或僅提供重試入口代替問題解決。可修復的資料、格式、引用、產物或治理工具／流程錯誤須在授權範圍內處理，不只重複同一失敗操作。未完成狀態仍允許受管修復入口與局部必要檢查；若故障由循環前置閘門造成，須修復該循環，恢復不得要求故障中的整套正式驗收先通過。修復保留原授權、保護其他修改並支援安全重試；完成後全套驗證仍須通過。持續失敗須依新證據調整方法，不能無界重試或因檢查失敗直接結束。確實依賴人類提供資訊／決策或外部狀態且無可安全替代方法時，先完成可行調查與修復準備，具體說明所需條件並請求最小必要協助，条件具備後續作解決；不得虛報完成或擅改契約。 |
| REQ-014 | 本次工程工作要以舊文件作執行依據時，自動準備本次 SPEC 及必要設計依賴的新格式工作／目前版本，無關歷史不整批改寫。依已採用分檔與欄位格式轉換，保留需求／決策／驗收 ID、內容語意、原始回答、實際驗證狀態及來源／版本關係，建立原檔至新檔與欄位對照。舊 manifest 的設計來源轉移至 Markdown 後，manifest 依新來源生成。純格式轉換具可核對的完整語意與來源證明時，沿用既有授權延續機制，保存證明並核對新文件集合後接續，不重複要求相同授權，不虛構歷史或新授權。 |
| REQ-015 | 新必填欄位缺漏先調查可信專案文件、已保存討論、平台資料及程式，依據明確才補足；無法確定或契約衝突時在新格式工作版提出具體待決事項並繼續討論，不假設設計或已驗證。新增規則造成需求、設計或驗收實質改變時先呈現差異並依既有要求確認。原確認版本／來源快照保留為不可修改歷史，與新工作版明確關聯，不把重排當作當時已確認新版；舊格式讀取僅供轉換與追溯，當前執行及檢查採新機制。遷移失敗依 REQ-012、REQ-013 解決，不以待遷移標記代替完成。 |
