# 驗收對照缺漏的通用修復與執行憑證核發

## Problem
治理流程先要求驗收對照完整才能核發執行憑證，但現有修復路徑先要求有效憑證，造成循環阻擋。問題適用任何 SPEC 與版本，不能以 SPEC-0058 第 6 版作為硬編碼條件。
來源程式：skills/engineering/implement/scripts/managed_delivery.py 的 authorize、_admit、_recover，以及 spec_delivery.py 的 verify_delivery_admission。已完成原始碼檢查，尚未完成修復實作或端到端重現測試。

## Solution
依 DEC-005 採用已呈現的通用驗收對照修復、授權與准入分離、持續同 SPEC 保存及 H1–H6 hook 檢查方案。執行授權來源 01a0b88d-1546-7473-af26-80fab66ac879。不延伸到發布、commit、燒入或自動信任 hook。

## User Stories
- 使用者遇到任何 SPEC 的驗收對照缺漏時，工具都應辨識並處理，不能只處理某一版本。
- 使用者可以直接開啟 working SPEC 查看討論與候選方案。
- 已授權同一版 SPEC 的使用者不因工具準備資料缺漏而被反覆要求同一授權。

## Candidate Design
以下設計原以候選提出，現依 DEC-005 採用。
1. authorize 先核對原始授權、任務及目前 SPEC；以獨立待完成申請保存授權來源、版本與雜湊；產品執行權保持 false。
2. 新增 repair-acceptance 受限入口，限於該 SPEC 的 validation/acceptance-SPEC-xxxx.json。缺漏應被普遍辨識；只有修補可由現有需求確定且授權有效時才自動套用，否則保留稿件並指出缺漏資訊。
3. 檢查 AC 存在性與修補差異，不允許刪除或降低驗收要求、偽造通過證據、修改 SPEC 或產品程式。不可僅信任 deterministic 呼叫端旗標。
4. 重新檢查全部准入條件；非對照問題仍須阻擋，修復成功不等於驗收完成。一般 recover 保留有效憑證要求。
5. 使用既有鎖、檔案雜湊與中斷恢復機制；同一申請重試不重複核發。撤銷或 SPEC 變更使原申請失效。既有授權僅在來源可核對且綁定相符時銜接，不偽造訊息。
6. SPEC 儲存時提早指出缺漏 AC 對照，允許保存 working 文件；不自動推定任意驗收方法。

## Candidate Hook Persistence Design
以下設計原以候選提出，現依 DEC-005 採用；實際 host 證據保持待驗證。
- H1 單一專案綁定：任務建立時以已選定 SPEC 或使用者選定的儲存庫保存 canonical project_root；hook、router、owner 共用同一綁定，另存 host cwd。父目錄含多個 repository 時不猜測第一個，也不把任意 cwd 改變當成改綁。沒有唯一根目錄時回報 mapping gap，保留討論來源，待解析後保存，不開第二份 SPEC。
- H2 工程 entry 建立 working SPEC：UserPromptSubmit 記錄真實 task/turn/source 的待分類事項；router 確認工程討論後即 start/resume。每回合形成來源對照表，區別採用、候選、事實、問題及非工程內容；不得用純關鍵字或前回合分類替代當前判讀。
- H3 逐項保存與檢查：reconcile 在 owner 中保存具來源的決定、影響的 REQ/DEC/AC、候選處置及版本。待保存／已保存狀態以原子寫入的實際文件及 journal 為依據，必須重新讀取確認；每個已識別的採用事項需有決定對照，不能僅用一段 summary 或 changed hash 宣稱完整。無修改內容只驗證、不強迫改版。
- H4 實際 hook 健康證據：分別顯示 supported、trusted、loaded、fired；記錄實際入口版本/雜湊、事件、task/turn、project root 及結果。未觀測到事件只標示 unverified，不宣稱未安裝或成功。不得自動開啟信任。缺少 hook 時由 agent 使用 owner CLI 等效保存，但標示 manual，不能算 host hook fired。
- H5 Stop 檢查 current turn、canonical path、revision/hash、待保存事項及 journal，而非只判斷存在摘要。首次漏存啟動既有有界修復；失敗仍可結束並明示 unsaved，保留可重試待辦。下回合先恢復待辦再依其作結論，唯讀調查及保存持續開放，產品操作依同步與原授權獨立判定。不增加無限重試或永久封鎖。
- H6 保存結果可見：owner 返回 ID/title/path/revision/status 及實际保存項目，agent 回覆列出連結與狀態；缺漏不得說已保存。工作階段保持 working；需求尚在討論時不得因有摘要或驗收欄位便自動 confirmed。
- 限制：機械檢查只能驗證已識別事項的完整映射，不能保證模型理解每個自然語言決定。以每回合來源覆蓋核對、明確待分類項目、人工可讀決定表及真實情境回歸降低漏判；不宣稱任何主機/工具全面攔截。

## Hook Value And Remaining Decision
依 DEC-005 保留 hook，主動保存由 agent/owner 負責；hook 為可驗證的第二道檢查。刻意略過保存時真實 host 必須攔截受涵蓋操作並要求補存，補存後解除。無真實 host 證據只能報未驗證，不能宣稱完成。

## Proposed Hook Validation
- 同一議題持續討論即持續寫入同一 working SPEC；以多種回合數的參數化長序列、重啟續談與中斷恢復驗證，不設三回合上限。每回合新資訊保存同一路徑、逐項保留來源與影響，未定事項可繼續討論。
- 候選建議不自動變為採用要求；使用者既有明確決定不反覆詢問；同一 turn 重播不新增重複決定，無改動不增加語意版本。
- host cwd 為父目錄、實際專案為子 repo 時 hook/router/owner 使用同一存放位置；多 repo 不默選。
- 摘要已存但已識別的採用事項缺漏時同步不得 PASS；stale binding、磁碟失敗、程序中斷、並行更新均不可假報成功。
- hook 未觸發／啟動失敗／逾時時狀態如實標示，手動 CLI 保存可完成但不可冒充 hook 證據。
- 真實桌面事件逐一驗證 UserPromptSubmit、PreToolUse、Stop 的 task/turn/root 對應；假事件單元測試不能取代主機證據。
- 自動修復耗盡後可報告未保存而結束；重啟不重置預算；來源或 runtime 實際改變後能重查，唯讀和保存不被永久阻擋。
- 保留原驗收對照修復方案的參數化回歸，不將任一 SPEC ID、版本、AC 編號寫死。
