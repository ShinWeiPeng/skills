# OS 與執行環境規劃治理

## Problem
使用者指出 OS 規劃未在 SPEC 中完整交代，要求開始討論通用 Skill 的補強。

## Solution
新增條件式 OS 程式規則，補齊平台／執行設計的九項適用性與七組具體欄位；以已採用公開 port／adapter 邊界與即時分析契約為基礎，明定三階段檢查。分檔、版本引用、格式解析與遷移機制由 SPEC-0044 提供。本文件修改方案已由使用者整體確認，尚未實作。

## User Stories
各專案可在確認 SPEC 前看見 OS 與執行環境的具體規劃及選擇理由。

### DISC-001: OS 規劃範圍
- **Situation:** 釐清共用 OS 規劃範圍。
- **Question:** 共用 OS 規劃的範圍採哪個方式？
- **Options and tradeoffs:** A：只規劃已指定 OS 的使用方式；OS 選型由專案另行決定。
  B：依單一專案需求規劃；已確認 OS 則沿用，未定案才比較並建議，由使用者確認。多 OS 支援另依需求提出（建議）。
  C：所有專案預設規劃多 OS 支援，定義共同介面及各 OS 實作與驗證；增加移植彈性及維護成本。
- **User answer:** 採用方案B
- **Explicit rationale:** 使用者未另提供理由；來源為本聊天對 Q-OS-SCOPE-001@2 的回覆。
- **Resulting impact:** 採用 REQ-001、DEC-001、AC-001；未授權實作。
### DISC-002: OS 規劃深度
- **Situation:** 決定 OS 規劃九項內容的呈現深度。
- **Question:** OS 規劃的九項內容應以什麼深度呈現？
- **Options and tradeoffs:** A：基本資料必填，其餘由 Codex 自行判斷是否展開；文件較少，但容易漏掉未呈現的設計決策。
  B：九項都判定適用性；適用項交代具體方法與理由，不適用項說明原因；時序分析與量測深度依風險及既有規範決定（建議）。
  C：所有專案都完整展開九項與詳細分析；查核一致，但簡單專案成本較高，仍不能捏造未取得的數據。
- **User answer:** 方案B
- **Explicit rationale:** 使用者未另提供理由；來源為本聊天對 Q-OS-DEPTH-002@4 的回覆。
- **Resulting impact:** 採用 REQ-002、DEC-002、AC-002；未授權實作。
### DISC-003: SPEC 分檔引用
- **Situation:** 單一 SPEC 同時包含需求、設計、驗收與討論歷史，使用者希望分檔維護。
- **Question:** 先釐清草案檢查入口：確認前的 OS／模組／資料流設計應保存在哪裡並如何供檢查器讀取？整體授權、正式轉換與驗收順序仍待後續確認。
- **Options and tradeoffs:** A：SPEC 內保存結構化設計草案，工具讀取並在記憶體或受限暫存區建立唯讀檢查輸入；正式 manifest 不變。確認前做設計檢查，需新增擷取及錯誤定位功能（建議）。
  B：SPEC 引用獨立設計草案檔，草案是候選設計的唯一可編輯來源；檢查器直接讀取。較適合大型設計，但須明定授權前可寫草案的範圍、版本綁定及清理方式。
  C：確認前只做文字與人工設計審查，授權後產生正式 manifest 才執行機器檢查。新增工具較少，但結構或引用錯誤可能到授權後才被發現。
- **User answer:** 我的想法是目前SPEC檔案內容有點多。可以把SPEC細分檔案，用引用的方式串起來。每個不同的設計都在各自的檔案進行維護。
- **Explicit rationale:** 使用者明確指出目前 SPEC 內容有點多，希望每個不同設計各自維護。
- **Resulting impact:** 新增 REQ-003、DEC-003、AC-003。分檔是已採用方向，具體結構仍待確認；未授權修改治理實作或搬移既有 SPEC。
### DISC-004: 專案共用設計文件
- **Situation:** 決定分檔設計文件的維護單位與生命週期。
- **Question:** 分開的設計文件要按每份 SPEC 保存，還是作為專案共用、持續演進的設計？
- **Options and tradeoffs:** A：每份 SPEC 擁有自己的設計文件；當次變更容易封存，但跨 SPEC 需處理重複及整合。
  B：每種設計在專案中只有一份目前版本，各 SPEC 引用相關設計及確認版本；候選修訂與歷史版本另有明確狀態，避免新草案改動舊確認內容（建議）。
  C：共通平台設計由專案共用，功能設計隨各 SPEC 保存；可分別管理，但須明確界定兩類文件與交叉引用。
- **User answer:** 方案B
- **Explicit rationale:** 使用者未另提供理由；來源為本聊天對 Q-SPEC-DESIGN-LIFECYCLE-004@9 的回覆。
- **Resulting impact:** 採用 REQ-004、DEC-004、AC-004；尚未選定具體候選修訂保存方法，未授權實作。

### OS 欄位承載與來源
平台基本事實與執行單元／資源清單用固定表格；巢狀通道契約、同步等待、生命週期條件與時序分析記錄用指定 YAML 區塊。每欄的格式、型別、單位、必填／適用性與來源在領域格式逐一列明，禁止兩處手填同一值。模組／介面／資料流依既有 ID 與版本引用，不複製其資料。
